# QuantaAlpha 盘中 T+1 机制影子盘使用手册

## 1. 定位

当前运行 ID：`intraday_shadow_20260910_t1_reversal_v9`

这是由 QuantaAlpha 后端自主运行的内部模拟盘。页面关闭、Codex 退出后，只要本机 supervisor 仍在运行，FastAPI worker 就会按 60 秒周期检查数据、冻结信号、结算账本并写证据快照。Codex 只用于开发和维护，不属于每日交易链路。

自主运行不等于当前已经具备完整生产实盘能力：本运行没有连接券商或真实资金，也不会自行研究、调参或承诺收益。锁屏和显示器休眠不影响当前 supervisor；注销或重启后的自动恢复仍要完成 macOS 登录项授权和实测。

当前实现是论文机制代理，不是论文复现，也没有盈利证明。依据是 SSRN 官方摘要《Delayed Feedback Trading and Return Reversals: Evidence from China's 'T+1' Rule》（DOI `10.2139/ssrn.6736959`）；论文全文方法尚未核验，因此本运行固定 `paperReplication=false`、`profitabilityProven=false`、`automaticPromotionAllowed=false`。

### 1.1 2026-09-09 状态结论

V6 已永久进入 `MISSED_SESSION`，不能恢复为有效前向运行。账本只有 2026-08-17、2026-08-18 两个有效结算会话；2026-08-19 至 2026-09-04 共 13 个交易日记录为 `DECISION_INTENT_DEADLINE_PASSED`。两个有效会话内 C1 累计收益约 -0.5229%，B0 约 -0.4114%，C1 相对 B0 约 -0.1120 个百分点。样本过少，不能证明策略无效；但更不能据此宣称盈利。

根因包含两类，必须分开处理：8 月 19 日只有 28 个成功时槽且无显式错误记录，约 15 分钟出现一次，较符合机器未持续运行的特征，但没有历史电源日志可直接证明；8 月 20 日与 8 月 31 日存在明确行情源错误。2026-09-07 上午也出现 94 个不可变错误时槽，11:29 后采集连续恢复，但当天仍不能作为新运行的完整资格日。

V5/V6/V7/V8 的声明、协调器、账本和证据快照继续只读保存，不补写任何漏日。V7 在 9 月 8 日完成一组有效的两阶段快照和决策绑定，但旧日频 Provider 维护器因无法证明已冻结旧 Provider 的追加谱系而无法推进正式日线；该未结算会话阻止 9 月 9 日生成新决策，系统已永久记录遗漏。V8 仅记录了零会话的声明检查点；在首个合格交易日前发现同一谱系错误还会发生在证据检查入口，因此其冻结实现不能修改。V9 在完成该 Provider-only 恢复修复后预声明，首个可产生证据的交易日是 9 月 10 日。它使用相同策略、成本、因果顺序和实时来源契约，但使用独立账本，不合并旧收益。

## 3. 每日自动流程

1. 盘中采集器每分钟保存 CSI300 + 基准的不可变快照和时槽哈希链；个股按腾讯 HTTP、easy_tdx 独立 TCP、东方财富 HTTP、新浪 HTTP 逐源检查现价、昨收、换手率和时效，基准只要求现价、昨收和时效。单条报价只能来自一个完整来源，禁止跨源拼字段。当天首个提交时槽同时锁定 Provider，盘中即使官方日线切换到新目录，后续时槽仍沿用该日首次绑定，避免数据集漂移。
2. 14:50 快照只负责计算 C1/B0 排名。14:50:00 至 14:54:30，worker 验证决策快照、逐只报价和组合状态后，先把两臂目标、排名合同、决策快照哈希和组合指纹写入 `decision_intents`，审计事件为 `DECISION_INTENT_FROZEN_BEFORE_EXECUTION`。
3. 14:55 快照只负责模拟成交价格。14:56:00 至 15:05:30，worker 必须先找到同日不可变决策意图，并重新核对决策快照、目标排名和组合指纹均未漂移，才允许给这些既有目标绑定 14:55 价格；审计事件为 `EXECUTION_PRICE_BOUND_TO_PRIOR_DECISION_INTENT`。
4. 两个阶段都要求关键快照为 301 个唯一代码、个股核心字段覆盖至少 95%、报价时效合格且基准可用；C1/B0 全部目标在对应时点都必须有可用报价。质量不合格时失败关闭，不以残缺横截面继续交易。
5. 决策快照尚未提交但仍在决策窗口内时返回 `WAITING_DECISION_SNAPSHOT`；成交快照尚未提交但仍在绑定窗口内时返回 `WAITING_EXECUTION_SNAPSHOT`。这两个状态用于处理采集器和 worker 的正常并发，不算错误。
6. 超过 14:54:30 仍没有有效决策意图，永久记录 `DECISION_INTENT_DEADLINE_PASSED`；已有决策意图但超过 15:05:30 仍不能绑定成交，永久记录 `EXECUTION_BINDING_DEADLINE_PASSED`。两种情况都进入 `MISSED_SESSION`，禁止事后补算；存在前一交易日未完成意图时，也禁止开启下一日决策。
7. 正式日线 Provider 发布当日数据后，系统验证它是根 Provider 的只追加继承，并读取正式 `factor`。终止且不可晋升的旧日频影子盘如因冻结谱系不可用而无法继续，不再阻断 Provider-only 维护；该模式不会读取或改写旧账本，也不会回填交易。V9 只结算自身已有的真实盘中两阶段证据日期。
8. C1/B0 在同一 SQLite 事务中结算；任一臂失败，两臂全部回滚。
9. 每次审计状态变化后生成只读 SQLite 证据快照和链式 manifest，逻辑账本哈希包含 `decision_intents`。
10. worker 重启时会恢复已写入但尚未完成协调的决策意图，并核对从首日起的全部冻结交易日；历史漏日会被发现并永久标记，不会静默跳过或重复成交。

C1/B0、会话状态和结算审计写在同一个 SQLite `BEGIN IMMEDIATE` 事务中。隔离验收已在
C1 完成写入、B0 尚未开始时对结算子进程执行真实 `SIGKILL`；恢复后数据库完整性为
`ok`，订单、NAV 和双臂持仓均未半提交，随后同一会话可完整重试并正常结算。生产账本
当前也只读确认使用 `WAL` 和 `synchronous=FULL`。这证明应用进程中途强杀的原子恢复，
不等同于真实断电、磁盘损坏或文件系统故障测试。

## 4. 页面使用

生产使用打开 [http://127.0.0.1:8000](http://127.0.0.1:8000)，进入“回测 > 研究影子盘”，查看“盘中 T+1 机制影子盘”卡片。`http://localhost:3000` 只是前端开发服务器，不是无人值守运行所必需。

生产后端会直接提供已构建的 `frontend-v2/dist` 页面、JS/CSS 和同源 API/WebSocket。
因此关闭 Vite 开发服务器不会中断模拟盘后台任务或 `8000` 端口页面；只有修改前端源码后
才需要重新执行构建并刷新页面以加载新静态文件。只有修改后端代码或运行配置时，才需要受控重启后端。

同一页面下方保留“旧日频研究记录（只读）”，用于审计历史 `RESEARCH_SHADOW` 账本。它的
状态、收益和禁用按钮不影响当前 V9，也不能用来判断 V9 是否失败；当前运行始终以
“盘中 T+1 机制影子盘”卡片中的 `当前 V9`、自动前检和证据快照为准。

正常首日开始前应看到：

- `当前 V9`
- `协议已冻结，等待首日`
- `自动前检 15/15`
- `检查 MM/DD HH:mm:ss`
- `后端自动运行`
- `观察交易日 0 / 120`
- `遗漏时槽 0`
- `证据快照 1`
- `连续错误 0`
- C1/B0 各自的 `持仓 N` 和 `实际仓位 X.XX%`
- `最近交易日时序` 的完整状态、成功/失败/缺口和最长不可用分钟数
- `质量门 301 标的`、`核心字段至少 95%`
- `核心字段逐源降级`
- `14:50 入选逐只校验`、`14:55 入选逐只校验`
- `先决策后成交`

`自动前检 15/15` 表示 supervisor 最近一次 15 项只读检查全部通过；旁边的
`检查 MM/DD HH:mm:ss` 是报告生成时间。报告超过 15 分钟未刷新时，页面按
`STALE` 失败关闭，不再显示为绿色；`NOT_READY`、`INVALID` 或缺失报告也不会被
解释为可运行。页面只显示脱敏摘要，完整诊断仍保存在权限 `0600` 的自动报告中。

`sessionContinuity` 独立读取冻结交易日历，并核对决策意图、待绑定意图、已冻结、已观察、
遗漏和最新会话。`causalOrder` 另行确认必须先写决策意图、禁止跨日悬挂并绑定组合指纹，
且两个窗口的先后关系有效。`sourceReliability` 不只读取冻结声明，还通过采集状态接口核对当前
后端实际导入的 `intraday_capture_v3` 入口、V3 Provider 类、`easy-tdx` 安装版本、逐条来源契约、
来源顺序和禁止跨源拼字段规则，并验证独立 TCP 与资格报告绑定。入口、类、版本或协议指纹任一
漂移都会失败关闭。任一到期交易日没有出现在证据中，整套前检也会失败并触发既有告警。这些
检查不写行情、账本或证据文件。

`captureHistory` 自 2026-09-14 起检查当天不可变时槽的连续性。当天有 `ERROR` 或缺口时，
即使最近一次采集成功、连续错误归零，预检仍为 `NOT_READY`，并沿用既有告警通道。
午休和收盘不会清除当天失败；下一交易日开始后按新一天检查，休市等待时保留前一日诊断但不将
其失败永久延续。哈希链损坏始终失败关闭。该运维检查不改变 V9 的关键快照质量门或交易资格，
也不把普通分钟采集失败直接改写成决策遗漏。

页面没有开始、补单、改参数或重置按钮。这些入口被有意省略，避免人工改变已经冻结的前向协议。

页面中的 `遗漏时槽` 只统计当前协议是否永久错过 14:50 决策意图或 14:55 成交绑定，
不是全天每分钟采集成功数。`当日可用覆盖 301 / 301` 也只描述最近一个成功快照的横截面
标的覆盖，不代表整天所有分钟时槽完整。页面的 `最近交易日时序` 会独立验证不可变
`slots/<交易日>/` 哈希链，并按已经到期的连续交易分钟显示成功、失败、缺口和最长不可用段；
红色 `时序不完整` 不会因为采集器后来恢复而消失，也不会触发事后补写。

`实际仓位` 按该臂全部持仓市值除以正式模拟总资产计算；它反映 A 股整手约束和剩余现金后的
真实资金暴露，不等同于冻结协议的 95% 目标风险仓位。正式日线尚未完成首日结算时，持仓数和
实际仓位都会保持 0。

## 5. 状态说明

| 状态 | 含义 | 操作 |
| --- | --- | --- |
| `STAGED` | 协议和首个证据快照已冻结 | 等待首个交易日 |
| `DECISION_FROZEN_AWAITING_EXECUTION` | 14:50 目标意图已冻结，尚未绑定 14:55 价格 | 无需人工操作，等待成交绑定窗口 |
| `AWAITING_OFFICIAL_DAILY` | 配对信号和成交价已冻结 | 等待正式日线，无需人工操作 |
| `ACTIVE` | 至少完成一个真实前向交易日 | 继续观察 |
| `MISSED_SESSION` | 当前运行的决策/成交关键时槽或会话连续性有永久缺口 | 停止本运行，调查原因；不得补算 |
| `RISK_STOPPED` | 任一臂最大回撤达到 15% | 停止新信号，人工复核 |
| `ERROR` | worker 周期失败 | 查看 readiness、automation 和后端日志 |

## 6. 运维检查

生产 supervisor 已通过 `.env` 的 `QA_BACKEND_INTRADAY_PREFLIGHT_ENABLED=true`
启用无人值守前检。后端 readiness 正常后，每 300 秒自动执行一次 15 项检查，并将
最新完整结果原子写入权限 `0600` 的
`data/results/intraday-shadow-readiness-latest.json`。失败只发送固定
`INTRADAY_PREFLIGHT_FAILED` 告警，不重启健康后端、不补算交易、不修改行情、声明或
账本；恢复后只发送一次 `INTRADAY_PREFLIGHT_RECOVERED`。

连续交易时段的 242 个预期分钟全部到期后，采集 worker 会再执行一次只读时序审计。
如果当天仍有不可变 `ERROR` 或缺口，它会通过同一固定告警通道发送
`INTRADAY_TEMPORAL_DEGRADED`。该事件按“事件类型 + 交易日”在权限 `0600` 的事件日志内
加锁去重，因此同一交易日即使后端或 supervisor 重启也最多发送一次。午休期间、尚未到期的
交易日以及完整交易日不会发送；事件只含固定说明和交易日，不含价格、股票、上游错误正文或密钥。
这项审计不会把失败分钟补写为成功，也不会影响当前运行的决策、成交绑定或正式日线结算。

需要即时复核或排障时，也可手工运行同一只读前检：

```bash
source scripts/qa_env.sh
python scripts/verify_intraday_shadow_readiness.py
```

输出 `status: READY` 且退出码为 `0`，表示主管、防休眠、三个 worker、采集计划、
当天采集连续性、校准、会话连续性、V9 运行、质量合同、因果顺序、来源可靠性、证据链、冻结声明与存储共 15 项当前均可用。输出
`NOT_READY` 且退出码为 `1` 时，查看 `checks` 中 `passed: false` 的项目，不要绕过
失败项启动人工补算。该命令不修改行情、声明或交易账本。

### 行情源拒绝原因诊断

出现“所有报价不可用”而无法确定原因时，可用已有的已验证快照提供股票池，运行一次独立探测：

```bash
source scripts/qa_env.sh
python scripts/diagnose_intraday_sources.py --reference-snapshot <已有快照的完整路径.json.gz>
```

该命令沿用冻结 V3 的逐源降级顺序，每个来源只统计返回数量、请求耗时、连接异常类型，
以及无成交/陈旧、错误交易日、过期、时间超前、价格无效、核心字段缺失等拒绝原因。
`atRequestStart` 对应现有客户端的检查时刻，`atResponse` 使用该来源响应到达时刻，
用于发现延迟响应导致的时间判断差异。只有实际进入的降级来源会被探测；东方财富内部已过滤
掉的报价不能从其返回结果还原。异常正文和行情价格不输出，结果仅写到终端。

这是独立请求的诊断，不会写生产时槽、交易或证据；它也不能追溯还原之前失败请求的原始响应。

## 8. 盈利判断

- 20 个连续交易日只通过工程门，不代表盈利。
- 60 个交易日且 C1 税费后超额和 C1 相对 B0 都大于 0，才形成早期数值证据。
- 120 个交易日保持上述条件，才形成较强前向数值证据。
- 即使达到 120 日，本运行也不会自动变成实盘或宣称论文有效；仍需审查成交容量、市场状态、收益集中度、成本敏感性及论文方法差异。
